# 参与上游讨论的记录原则

这个仓库记录的是个人学习和实验。参与上游讨论时，个人结论与项目官方结论必须分开表达。

## 先形成证据

在评论或提交 PR 前，尽量准备：

- 上游仓库、分支和 commit；
- 操作系统、ROCm、Python、PyTorch、Triton 和 GPU 型号；
- 可直接执行的复现命令；
- 最小输入和实际输出；
- 预期行为及其来源；
- 已经排除的环境因素。

只说“运行失败”通常无法帮助维护者定位问题。把失败缩小到单个算子或单个测试更有价值。

## 尊重已有工作

提问前先搜索 Issue、PR 和相关源码。DeepInfer 的 ROCm 工作已经按 #202–#206 拆分，新的讨论应说明与现有工作的关系：

- 是独立复现；
- 是补充测试；
- 是发现回归；
- 是提出一个小范围改进。

避免重复提出范围更大的整体方案，也不要把他人的完整实现描述成自己的移植成果。

## 提问方式

比“我可以帮忙吗”更有效的表达是：

> 我在 `commit / 环境` 中复现了 `命令`。该用例预期 `X`，实际得到 `Y`。我已排除 `Z`。我准备补充一个只覆盖 `场景` 的测试或补丁，想确认这是否符合当前方向。

这类评论同时提供背景、证据、最小范围和下一步，维护者更容易判断。

## 提交范围

- 一个补丁解决一个明确问题；
- 不把格式化、重构和新功能混在同一提交；
- 修改 vendor 代码时保留原许可证和来源；
- 新增测试要说明与其他测试的区别；
- 性能改动同时提供正确性验证和可复现 benchmark。

## 归因和许可

- 引用源码时链接到具体文件或 commit；
- 复制代码前检查原项目许可证和通知要求；
- 个人仓库不暗示自己代表 DeepInfer 官方；
- 评审建议即使没有被采纳，也保留讨论链接和背景，不删除记录。
